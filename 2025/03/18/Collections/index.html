集合

一、集合和数组的区别

1.数组是长度固定的数据结构，一旦创建长度就无法改变。集合是长度可变的数据结构，可以根据需要动态的增加或减少元素

2.数组可以存储基本数据类型和对象，集合只能包含对象

3.数组可以直接访问元素，而集合需要通过迭代器或其它方法。

4.数组的功能简单，仅支持元素的存储和遍历。集合提供丰富的API，如（添加add()、删除remove()、查找contains()、排序sort()）等。

5.数组在运行时检查类型的一致性，集合使用泛型时，在编译时检查类型，避免类型错误。

二、集合

List

List是有序的Collection，使用此接口能够精准的控制每个元素的插入位置，用户可以根据索引访问List中元素。常用的实现List的类有ArrayList, LinkedList, Vector, Stack.

1.ArrayList

底层使用数组实现，非线程安全。支持对元素的快速随机访问，但插入和删除速度很慢。可以放null值，且元素可以重复。

扩容机制：

ArrayList中维护了一个Object类型的数组elementData。

当创建对象时，如果使用的是无参构造器，则初始的elementData容量为0，在第一次add()的时候，elementData的容量扩容到10，如果需要再次扩容，则按1.5倍来扩容。

如果使用指定大小的构造器，则elementData容量为指定大小，如果需要扩容，则直接扩容elementData为1.5倍。

2.LinkedList

底层维护了一个双向链表，可以添加任意元素，可以重复包括null,线程不安全，没有实现同步。添加和删除效率高

3.Vector

底层也是Object对象数组，Vector是线程同步的，即线程安全，Vector类的操作方法带有synchronized，效率不高。

扩容机制：如果使用无参构造，默认初始容量为10，如需扩容，按两倍扩容；如果使用有参构造，elementData大小为指定大小，扩容时为elementData两倍。

Set

Set不允许存在重复的元素，与List不同，set中的元素是无序的，不能使用索引获取数据。常见的实现类有HashSet,TreeSet，LinkedHashSet

1.HashSet

底层实际上是HashMap。可以存放null，但只能一个，即元素不能重复。不能保证存放元素的顺序和取出顺序一致，但每次取出的顺序一致。

添加元素时，先得到hash值-会转成->索引值。找到存储数据表的table，看这个索引位置是否已经存放有元素。如果没有，直接加入。如果有，调用equals比较，如果相同，不加入，如果不同，则添加的到后面。

如果一条链表的元素个数大于等于8，并且table的大小大于MIN_TREEIFY_CAPACITY（默认64）就会进行树化

扩容机制：HashSet的构造函数允许指定初始容量和负载因子，默认情况下，初始容量为16，负载因子为0.75，和HashMap一致。当元素的数量达到容量*负载因子时，会自动扩容为当前容量的两倍。

参数 默认值 含义
初始容量 16 初始桶数组的大小（2的幂）
负载因子 0.75 触发扩容的填充阈值（容量 × 负载因子）
哈希冲突阈值 8 单链表超过该长度转为红黑树（Java 8+优化）
降级阈值 6 红黑树节点少于该值转回链表（Java 8+优化）

当满足以下任一条件时触发扩容：

完整扩容流程

  1. 创建新数组：容量翻倍（如 16 → 32），确保维持 2 的幂次方特点。

  2. 重新哈希（Rehash）

    • 遍历原桶数组中的所有元素（包括链表/红黑树节点）
    • 对每个元素重新计算哈希值：(e.hash & (newCapacity - 1))
    • 分散到新数组的对应桶中（可能调整到高位或低位）

  3. 迁移后的结构调整

    • 若某桶链表长度在迁移后 ≤ 6，将红黑树退化为链表

    • 新数组开始接收后续新增操作

      • 误区1：“HashSet的初始容量可以随便设置”
        → 实际会强制对齐到最近的2的幂次方（如设5→8；设17→32）
      • 误区2：“负载因子越大性能越好”
        → 负载因子高意味着更迟触发扩容，但哈希冲突概率增加，链表或树结构可能影响性能
2.TreeSet
3.LinkedHashSet

LinkedHashSet是HashSet的子类，底层是LinkedHashMap，底层维护了一个数组加双向链表。LinkedHashSet根据元素的hashCode值来决定元素的存储位置，同时使用链表维护元素次序，这使得元素看起来是插入顺序保存的。不允许添加重复数据。

Map

Map是一个键值对集合，存储键、值之间的映射。key无序，唯一；value不要求有序，允许重复。主要实现有HashMap,TreeMap,HashTable,LinkedHashMap,ConcurrentHashMap。常用方法（添加add()、删除remove()、根据键值获取get()、获取元素个数size()、判断是否为空isEmpty()、清除clean()、查找键值是否存在containsKey()）。

以下是Map（以HashMap为例中 Node、Entry和EntrySet的关系解析图）

组件 作用 内存效率
Node 实际存储键值对的哈希链表/树节点，直接承载数据读写。 直接操作内存
Entry Node 的接口形态，提供对 key 和 value 的访问与修改。 无内存开销
EntrySet 基于 Node 数组的视图集合，通过惰性遍历避免数据复制。 零拷贝
1.HashMap

底层是数组+链表+红黑树。 线程不安全。

扩容机制：同上HashSet。HashMap底层维护了一个Node数组，默认为空。当创建对象时，将加载因子初始化为0.75.当添加key-value时，通过key的哈希值计算出索引。然后判断该索引处是否有元素，如果没有直接添加。如果有，继续判断该元素的key和添加元素的key是否相等，如果相等，直接替换value；如果不想等需要判断是树结构还是链表结构，做出相应处理。如果添加时发现容量不够，需要扩容。

第一次添加，table容量扩容到16，阈值为12；以后再扩容，则需要扩容table容量为原来的两倍。

在Java8中，如果一条链表的元素个数超过8，如果此时的table容量小于64，会先尝试扩容。如果大于等于64，会触发树化机制。

在 JDK 1.7 和 JDK 1.8 中，HashMap 的实现经历了显著优化，主要改进集中在数据结构、哈希冲突处理、扩容机制及性能方面。以下是具体变化及对比：

  1. 数据结构的变化

JDK 1.7：数组 + 单链表

  • 冲突处理：使用单向链表解决冲突，新元素插入链表的头部（头插法）。
  • 缺点：
    • 频繁哈希冲突时，链表过长会导致查询效率退化至 O(n)。
    • 并发扩容时，头插法可能产生循环链表，导致死循环（非线程安全引起的问题）。

JDK 1.8：数组 + 单链表/红黑树

  • 优化引入红黑树：当链表长度超过阈值（默认 8）时，链表转换为红黑树；当节点减少到阈值以下（默认 6）时，红黑树退化为链表。
  • 优势：
    • 在极端哈希冲突情况下，查询效率仍能保持 O(log n)。
    • 降低哈希攻击（人为构造冲突）带来的性能风险。

2. hash 方法的优化

JDK 1.7：四次扰动

  • 多次位扰动降低碰撞概率，但计算较复杂。

JDK 1.8：简化扰动（一次异或）

  • 高位与低位参与散列：将哈希码的高 16 位与低 16 位异或，充分利用哈希值。
  • 计算更高效，同时分散性更好，间接减少转红黑树的概率。
  1. 插入与扩容机制

插入方式

  • JDK 1.7：头插法（新元素插入链表头部）。
    • 问题：并发扩容时可能出现循环链表（如两个线程同时扩容）。
  • JDK 1.8：尾插法（新元素插入链表尾部或红黑树）。
    • 避免循环链表问题，但多线程下仍有数据覆盖风险（需用ConcurrentHashMap）。

扩容时机

  • JDK 1.7：先扩容再插入（插入前检查size >= threshold）。
  • JDK 1.8：先插入后检查扩容，在插入完成后触发resize，逻辑更统一。

扩容后数据迁移

  • JDK 1.7：
    1. 原数组的每个链表重新计算索引（indexFor）。
    2. 遍历链表，按新容量逐个迁移节点。
  • JDK 1.8：
    1. 利用规律：新索引 = 原索引 或 原索引 + 原容量。
    2. 通过位运算快速定位位置（e.hash & oldCap），拆分链表/红黑树，迁移效率更高。

4. 线程安全性

  • 均非线程安全：HashMap本身设计不考虑多线程，但 JDK 1.8 解决了 1.7 中因头插法导致的循环链表问题。
  • 并发问题依然存在：多线程put可能导致数据覆盖或丢失，需改用ConcurrentHashMap。

5. 性能对比

场景 JDK 1.7 JDK 1.8
哈希冲突较少 O(1)（链表短） O(1)（同 1.7，但计算更快）
哈希冲突严重 O(n)（链表长） O(log n)（红黑树优化）
并发扩容 可能导致循环链表 数据覆盖，但无死循环问题
扩容数据迁移 遍历重新计算索引 按高位拆分，效率更高

总结

  • JDK 1.8 的改进：

    1. 数据结构：链表与红黑树结合，解决长链表查询效率问题。
    2. hash方法：优化扰动逻辑，减少碰撞。
    3. 扩容机制：迁移算法更高效，利用位运算快速定位新索引。
    4. 插入方式：尾插法避免多线程扩容死循环问题（但并发仍需其他手段保证安全）。

  • 实际影响：
    在哈希碰撞频繁的场景下（如恶意攻击或设计不当的哈希函数），JDK 1.8 的 HashMap 性能显著优于 1.7，同时在高并发场景下更稳定。
